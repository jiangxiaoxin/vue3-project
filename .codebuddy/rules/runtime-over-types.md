# 运行时优先：类型报错不阻塞交付

本项目是 Vue 3 + Vite 的实验 / 演示型仓库，`src/views` 下包含大量相互独立的 demo 页面。
**代码能否正常运行是唯一的验收标准。TypeScript 类型错误只要不影响运行，就不需要处理。**

## 铁律

1. `npm run type-check`（vue-tsc）在本仓库长期失败（数百条既有报错），这是**已知的既有状态**，不是待修问题。不得因为 type-check 报错而阻塞交付、回滚改动或拒绝完成请求。
2. **不要为了消除类型报错而修改代码**。禁止：为过类型检查而重构既有代码、引入复杂类型体操、改动运行时逻辑、增删业务分支。
3. **不要主动顺手清理历史类型错误**，除非用户明确要求。库存报错（大量 `TS7006` 隐式 any、`TS2307` 缺模块声明、`TS2339` 属性不存在等）维持原状即可。
4. 需要时**直接使用** `any`、`as` 断言、`@ts-ignore` / `@ts-expect-error`、`// eslint-disable-next-line` 来通过检查，不必为此额外解释或道歉。
5. `src/views/code-runner/**` 下**故意**保留了会类型报错的 TS 教学示例，属正常现象，**禁止删除或修正**。`src/views` 下其余 demo 页同样允许宽松写法。
6. lint 同规则：纯格式 / 规范类报错不阻塞；只关注会造成真实功能缺陷的问题。

## 例外：仅在以下情况才处理类型错误

- 会导致**运行时崩溃**或明显功能异常；
- 本次改动**新引入**，且能低成本顺手修掉；
- 出现在构建相关配置文件（`vite.config.ts` / `vitest.config.ts` / `playwright.config.ts`）中 —— 这类错误可能真正影响构建与测试执行。

## 验收优先级

1. `npx vitest run` —— 单元测试通过（最高优先级）
2. `npm run dev` —— 能启动、页面功能正常
3. `npx vite build` —— 生产构建成功
4. `npm run type-check` —— **仅供参考，失败不阻塞**

前三项通过即视为交付成功。不要在最终报告里把第 4 项的失败当作遗留问题反复强调；若类型错误确有运行时征兆，再单独指出。
